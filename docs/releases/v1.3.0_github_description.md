# Release v1.3.0 - Process Isolation, Hardware-Independent Engine Selection, and a Real-Audio Validation Layer

This release moves every vendor runtime out of the API process, makes engine selection
independent of the hardware it runs on, and adds the multilingual test corpus and remote
validation tooling that found most of the defects fixed below.

The theme running through it is a single failure mode: **a service that reports an
accelerator while quietly running on the CPU.** Several separate instances of that are
fixed here, and the guards added alongside them exist so it cannot happen silently again.

---

## Highlights

### Process Isolation (Architecture Change)

Engines and vocal separation now each run in their own worker process, behind a shared
duplex channel (`modules/inference/engines/worker_channel.py`).

Vocal separation is isolated on supported units only. Pre-Alchemist Intel graphics are the
exception: the UVR worker dies with SIGSEGV on Intel UHD, so isolation is gated on the
OpenVINO-reported GPU generation (`isolation_policy.py`) and separation stays in-process
there -- which means the crash containment described below does not apply on those hosts.

Three reasons, in order of weight:

- **Device-memory reclamation.** Killing a process is the only way to return a
  CUDA/ROCm/OpenVINO context's memory to the OS. In-process teardown reclaims none of it:
  an idle purge logged `CUDA VRAM=193 MB -> 193 MB (Delta: +0 MB)`.
- **Crash containment.** A native segfault in CTranslate2, ROCm or the OpenVINO GPU plugin
  used to kill the API process. It now kills one worker, which respawns on the next call.
- **Mutually exclusive runtimes.** One interpreter cannot hold a CUDA context and an
  OpenVINO GPU context, nor a CUDA torch build and a ROCm one. Separate processes are the
  only way to run them together — which is what lets a hybrid host drive both cards.

Controlled by `ASR_ISOLATE_ENGINES` and `ASR_ISOLATE_PREPROCESSING` (both on by default).
The channel handles generation stamping so a cached handle cannot outlive the worker that
issued it, segment streaming, and cooperative cancellation across the process boundary.

### Engine Selection No Longer Depends on the Hardware

- **`ASR_ENGINE=AUTO` now resolves to `FASTER-WHISPER` on every host.** Previously AUTO
  picked a different engine per accelerator, which made the decoding behaviour — and
  therefore the transcript — a property of whichever machine a request landed on. One
  engine everywhere makes a deployment reproducible across a fleet.
- **`HYBRID_ENGINES` is off by default and opt-in.** On a host with both a CUDA/AMD GPU
  *and* an Intel GPU/NPU, `true` runs each unit's native engine in its own worker so both
  accelerators stay busy — at the cost of reintroducing per-unit engine variation.
- **`ASR_DEVICE` is now aligned with what the engine can actually drive.** CTranslate2 has
  CUDA and CPU backends and nothing else, so on Intel or AMD the device is reported as CPU
  rather than naming a device it cannot address. The unit stays in the pool for vocal
  isolation, which reaches it through ONNX Runtime.

Accelerator-specific engines remain available; they are now asked for explicitly
(`ASR_ENGINE=INTEL-WHISPER`, or `OPENAI-WHISPER` with the `amd-rocm-torch` image).

### Code-Switched Audio

- **Per-window language re-detection** (`multilingual=True`) for auto-detected requests.
  An explicitly requested language keeps the single-language path, because the flag
  overrides the request *and* misreports what it returned.
- **Gap-filling re-transcription** (`modules/inference/runtime/gap_filling.py`): speech VAD
  confirms but no segment covers is re-transcribed in its own detected language. Fixes the
  recorded dropped-code-switched-legs defect and, as a side effect, segments stopping short
  of the clip end. Costs one VAD pass and nothing further when there are no gaps.
- **`segment_languages`** is reported per response, so a code-switched file says where each
  language was found.

### Bug Fixes

- **Transcripts were being truncated on the way to the client.** History truncation mutated
  `task_data["result"]` in place — the same object the request handler returns — while
  `log_completed_task` only shallow-copied afterwards. Measured on a 20-minute clip: 169
  segments reaching 1202s were delivered as 100 segments ending at 765s. This had been
  recorded as an ASR "coverage" defect for some time; it was never the ASR.
- **AMD acceleration was silently disabled in every image.** ROCm pruning deleted
  `librocsolver.so.0`, which the ONNX Runtime ROCm provider links directly. ONNX Runtime
  treats a provider that fails to `dlopen` as merely unavailable — `get_available_providers()`
  still listed `ROCMExecutionProvider` while every model ran on the processor.
  `scripts/docker/verify_ort_provider_links.sh` now fails the build on an unmet provider
  dependency, so this class of fault cannot ship again.
- **OpenVINO reported an NVIDIA card as a plain Intel `GPU`**, which registered it as an
  Intel unit, handed it `INTEL-WHISPER`, and returned 500 for every request routed there —
  31 failures across the real-audio suite on the `full` image. Vendor identity now comes
  from `DEVICE_ARCHITECTURE`'s PCI vendor id.
- **The Intel NPU built a pipeline it could not execute.** The service started healthy,
  printed `ASR Runtime: OpenVINO (NPU)`, and failed every request. `modules/core/device_probe.py`
  inspects the OpenVINO IR for dynamic shapes — metadata, not a trial run — and ASR falls
  back to the CPU while the NPU keeps doing preprocessing, which it does run.
- **The ONNX variant was chosen from `ASR_DEVICE` before `ASR_PREPROCESS_DEVICE`.** On a
  hybrid NVIDIA+Intel host this loaded onnxruntime-gpu, which carries no OpenVINO provider,
  so `ASR_PREPROCESS_DEVICE=GPU` ran UVR on `CPUExecutionProvider` while the logs named the
  iGPU — 0.48x against 2.40x, five times slower while claiming acceleration.
- **Runaway decoding on the Intel engine.** `repetition_penalty` (not
  `no_repeat_ngram_size`, which `WhisperGenerationConfig` accepts and silently ignores)
  breaks the loop. Applied to greedy decoding only: OpenVINO GenAI rejects it under beam
  search with a hard error, which is the CPU path and the NPU-fallback path.
- **`openai-whisper` language detection failed on every short slice**, because the audio was
  not padded to the encoder's 30-second window before the mel was built. Gap-filling detects
  on sub-second slices, so this recovered nothing on that engine while still returning 200.
- **A full temp volume aborted startup** instead of falling back to persistent storage.
- **The inference chip on the dashboard was always a guess.** `FasterWhisperEngine` never
  recorded the device it loaded on, so the isolated proxy had nothing to report and the chip
  fell back to predicting from configuration on the project's most common engine -- with
  isolation on, which is the default. It now reads the device back from the CTranslate2
  handle, which also catches a CUDA request quietly served on the CPU.
- **One transient UVR failure demoted a unit to CPU isolation for the life of the process.**
  The CPU-fallback path restored the manager's device fields but not the separator it had
  built, so every later run reused the CPU one -- a performance fault and a reporting one at
  once, since the dashboard honestly reported CPU ever after.
- **`VAD_THRESHOLD` was ignored on `INTEL-WHISPER`.** The pipeline sends the nested
  `vad_parameters` dict that faster-whisper's API takes; the Intel engine read only the flat
  names, so the value fell through to a hardcoded `0.35` that matched neither the request nor
  the configured default of `0.5`. Intel ran a different VAD sensitivity from every other
  engine.
- **`VAD_FFMPEG_TIMEOUT_SEC=0` meant "expire immediately"**, failing every decode, where the
  only sensible reading is "no limit".
- **A half-provisioned OpenVINO IR cleared the NPU.** The probe skipped absent parts, so an
  export with its encoder written and its decoder still downloading inspected clean and
  logged "all statically shaped" on half the evidence. A missing part now counts as
  unverified, and a wholly absent IR is still reported differently from an incomplete one.
- **The Silero VAD checksum matched no artefact at its pinned tag**, so the optional
  pre-baking path failed every fetch. Re-derived from the `v5.1.2` bytes and verified by
  loading the model and running inference; the constant now carries that provenance.
- **A cancelled batch language detection leaked its worker stream**, leaving the worker
  decoding windows into a pipe nobody would read while the channel lock was held to its
  deadline.
- **OpenVINO's `DEVICE_ARCHITECTURE` was trusted without a vendor id.** A string carrying no
  `vendor=` field was read as Intel and could enable an isolated worker on silicon known to
  segfault in one. Only a confirmed Intel vendor id is now accepted.

### Vocal Separation Is Off By Default

Measured on an RTX 5090, two runs per mode, byte-identical:

| | off | on | |
| --- | ---: | ---: | --- |
| clean speech overlap | 0.9469 | 0.9469 | no gain at all |
| harder tail languages | 0.7994 | 0.7826 | loses 1.7 points |
| window misses (of 118) | 54 | 55 | |
| hallucinated quiet (of 25) | 12 | 10 | its one real win |
| long-form RTF | 0.063 | 0.110 | 76% slower |

76% more compute to remove two hallucinated windows in twenty-five. Still worth enabling
for music-heavy source material, which is not what the corpus represents.

### Local-Path Reads Are Reviewable

`local_path` lets a client name a file for the service to open instead of uploading it, and
which paths are permitted is decided by the approved roots. Those roots include every
non-system bind mount the container has -- which is what makes a mounted media library work
without further configuration, and is also an authorisation granted implicitly, with no
record that it happened.

The grant is unchanged by default, so existing deployments keep working, but it is now
visible and refusable: the auto-approved mounts are named in a startup log line, and
`WHISPER_AUTO_APPROVE_MOUNTS=false` drops that source entirely and confines local-path reads
to `WHISPER_APPROVED_ROOTS`. Deployments that turn it off must list their media roots
explicitly.

### Intel: Vocal Isolation Out of Process, Gated by GPU Generation

Isolated UVR separates at 4.6–5.0x through `OpenVINOExecutionProvider` on an Arc 140T,
against 0.25x when the in-process manager falls back to the CPU provider. It is not safe
everywhere: on Intel UHD Graphics the worker dies with SIGSEGV, intermittently — the first
request succeeds and a concurrent pair kills it, so a single green run proves nothing.

The variable is the GPU generation, not the software. `DEVICE_ARCHITECTURE` separates them
cleanly (`v12.0.0` on the part that crashes, `v12.74.0` on the part that does not), and
`modules/inference/pipeline/preprocessing/isolation_policy.py` gates on Alchemist-or-newer.
Anything unidentifiable keeps the in-process manager, because guessing wrong costs a native
crash rather than a slow path.

### The Dashboard Says Where Each Stage Actually Ran

A unit in the scheduler pool is where a task is *dispatched*, never where it executes, and
the two diverge constantly: CTranslate2 has no OpenVINO or ROCm backend, torch has no NPU
backend, and UVR falls back to `CPUExecutionProvider` whenever the image ships no provider
for the target device. All of that was invisible on a card showing only the unit's name.

Each hardware unit now reports `asr_execution` and `uvr_execution` -- the device that ran the
work, whether it was accelerated, whether an accelerator unit fell back to the CPU, and
whether the answer was *measured* from a live engine or predicted from configuration. A
loaded object always wins, because only it knows it moved: `IntelWhisperEngine` rewrites its
own device after a failed NPU warmup, and the separator's ONNX provider list is ground truth
even from inside a worker process.

The scheduler pool rule changed to match: a unit stays if it can accelerate **either**
decoding or vocal isolation. An Intel iGPU that CTranslate2 cannot address still runs a
complete task -- isolation on the iGPU, decoding on the CPU -- so a hybrid host now fills two
scheduler slots where it previously filled one. A unit that accelerates neither is still
dropped, and nothing claims an accelerator it is not using.

### Performance

- **Compiled-kernel caches now persist** across container restarts (SYCL, NEO, CUDA, Triton,
  Numba, all under `model_cache/kernel_cache/`). Intel cold start fell from 517.8s to 39.7s.
- **`ENABLE_LD_REQUEST_COALESCING`** collapses identical concurrent `/detect-language`
  requests onto one execution.

### AMD / ROCm

- Build-time verification that no bundled ONNX Runtime provider has an unmet dependency,
  with a documented allowlist for libraries supplied at runtime (`libcuda.so.1`, injected by
  the container toolkit) or deliberately absent (TensorRT, `libpython` for ROCm's unused
  Python bindings).
- `gfx1036` (the display iGPU in desktop Ryzen parts) is documented as unusable and why:
  `HSA_OVERRIDE_GFX_VERSION=10.3.0` gets ONNX Runtime's own kernels running correctly on it,
  then fails in rocBLAS, whose upstream Tensile library has never included that architecture.
  A GPU that can add but cannot multiply matrices is of no use to Whisper or UVR.

### Real-Audio Test Matrix

A generated multilingual corpus replaces the single English fixture: 40+ languages via Piper
and MMS-TTS, code-switched clips, degraded and malformed audio, and a 20-minute long-form
stress clip. Rendering is content-addressed and deterministic (the manifest pins the VITS
noise terms to zero), so committed fixtures round-trip with an empty diff.

- `scripts/audio_matrix/` — the generator; `scripts/generate_fixtures_docker.sh` runs it in a
  container so the TTS toolchain never touches the host.
- `tests/real_audio/` — accuracy, contract-abuse, degraded-input and long-form suites.
- The long-form clip has a **natural** layout profile measured from two genuinely
  code-switching films, because the original layout made utterance segmentation look far
  easier than it is: ~60% of real turns are separated by less than a VAD split threshold.

### Remote Hardware Validation

This machine cannot validate silicon it does not have. `scripts/remote_validate.sh` points at
a host that does — preflight, hardware audit, sync, build, run, and a tiered test suite —
with `scripts/validation_matrix.sh` driving several machines in parallel from an
operator-local plan (`.validation-matrix.conf`, gitignored, since it names hosts). Windows hosts are
driven through WSL2. Setup helpers exist for Linux, Windows and macOS in both shell and
PowerShell. See `docs/REMOTE_VALIDATION.md`.

It also carries the project's first controlled engine comparison — one machine, one image,
one corpus, only `ASR_ENGINE` changed:

| metric | FASTER-WHISPER | WHISPERX | OPENAI-WHISPER |
| --- | ---: | ---: | ---: |
| mean word overlap (24 clips) | 0.8675 | **0.8719** | 0.8716 |
| long-form RTF | 0.0299 | **0.0134** | 0.1179 |
| 24 short clips, wall clock | **26.1s** | 34.5s | 405.5s |
| hallucinated quiet windows (of 25) | 8 | **0** | 11 |

### Images

- **Every standalone target failed to build from a cold cache**, and the build cache hid it:
  a target's final-stage `RUN` only re-executes when the context changes, and CI's
  `cache-from` masked it the same way. `strip_build_artifacts.sh` ends by deleting
  `/var/lib/apt/lists`, then runs again in each target's final layer where it called a bare
  `apt-get purge` against an empty package index -- `E: Unable to locate package gcc`, exit
  100, dead under `set -euo pipefail`. It now selects the installed subset with `dpkg-query`
  and purges only that, so a genuine purge failure stays fatal. `amd-rocm-torch` failed
  separately on `libhipsparse.so.4`, which torch's bundled MAGMA links; hipSPARSE is now
  installed in that layer alone, so `amd` and `full` do not carry rocSPARSE for a torch build
  they never load. All nine targets verified building from a cold cache.
- The **`full`** image is the default build target again, and carries every vendor's ONNX
  Runtime, so one tag runs on whatever hardware the host turns out to have.
- Images stamp `WHISPER_IMAGE_EDITION`, reported alongside `VERSION` on the dashboard —
  two containers can run the same version with very different accelerator support.

### Code Quality

- Every Python module is inside the project's 600-line limit; `config.py`, `model_manager.py`
  and the preprocessing package were split along their existing seams
  (`config_resolution`, `config_paths`, `config_model_paths`, `gap_filling`,
  `preprocessor_pool`, `isolation_policy`, `init_locks`).
- `pylint` 10.00/10 with no messages, `ruff` format + check, `flake8`, and PowerShell
  ScriptAnalyzer all clean.
- `scripts/` is linted too. It had been excluded from `ruff`, which made it the only Python
  here that nothing checked -- and that is where a bare `except:` and several dead imports
  had survived.
- Shell linting (`shfmt`, `shellcheck`) covers all 22 scripts rather than the three it
  reached before; both cold-build failures above lived in files it was not looking at.

## Known Limitations

- **AMD ROCm remains unverified on supported silicon, and the dashboard will say otherwise.**
  The `full` image was validated on a real NVIDIA + Radeon host and splits the stages exactly
  as designed: ASR on CUDA (CTranslate2 has no ROCm backend) and vocal isolation routed to the
  AMD unit, with `Resource Pool: cuda:0, amd:0` and each unit correctly reporting a CPU
  fallback for the stage it cannot drive.
  **That is not AMD acceleration.** The card is `gfx1036` (Raphael integrated Radeon) and the
  image ships kernels for `gfx1030 gfx1100 gfx1101 gfx1102 gfx1200 gfx1201` only. ONNX Runtime
  loads the ROCm provider regardless, so `/status` reports `UVR = AMD GPU, measured: true,
  fallback: false` and the log reads `Isolation complete on AMD GPU 0 [ONNX: ROCMExecutionProvider]
  ... Speed: 3.03x` -- while
  the work runs on the processor. This is the documented AMD failure mode: a card whose
  architecture is absent still initialises and still transcribes, silently on the CPU. Read
  `measured` as "the provider list said so", which for every other vendor is the same thing and
  for AMD is not. A supported Radeon (RDNA2/3/4 from that list) is still needed.
  Reproduced independently on a second machine (RTX 5090 + Granite Ridge integrated Radeon,
  `1002:13c0`, 2026-09-08): same `gfx1036` class, same `UVR = AMD GPU, measured: true,
  fallback: false`, same ~3x speed. Two unrelated hosts producing the identical false positive
  makes this a property of the combination, not a quirk of one machine -- so treat any AMD
  acceleration claim from an unlisted architecture as unproven until `rocminfo` on that host
  shows an architecture the image actually ships kernels for.
- **The Intel NPU cannot execute Whisper.** It is detected, kept in the pool, and used for
  vocal isolation, which it does well. ASR on that unit runs on the CPU.
- Two long-form defects remain open and are tracked in the test suite as known defects:
  window misses and hallucinated speech in quiet passages.
- **Isolated OpenVINO alongside CUDA is reasoned, not measured.** A preprocessing worker is
  started with `CUDA_VISIBLE_DEVICES=""`, so no CUDA context can exist in it and OpenVINO is
  left in place there. No host with both an NVIDIA GPU and an Arc-class Intel GPU was
  available to demonstrate it; the in-process case, where the block still applies, is
  measured on an RTX 3080 + UHD Graphics laptop.
- **OPENAI-WHISPER needs more than 8 GB of VRAM for `large-v3`.** torch loads the model
  unquantized, so an 8 GB card fails at load with `OutOfMemoryError: CUDA out of memory`
  (measured on an RTX 3080 laptop GPU, 7.66 GiB total). FASTER-WHISPER runs on the same card
  because CTranslate2 quantizes. The engine is validated on hosts with room for it -- an RTX
  5090 and the Intel XPU image -- so this is a sizing note, not a defect.
- **The Intel NPU was validated for preprocessing only.** Both NUC runs used `--device GPU`,
  and the shipped Whisper IR cannot execute on the NPU regardless, so no NPU *ASR* claim is
  made anywhere in this release.

## Verification

- **Full local suite**: 2250 passed, 171 skipped, 0 failed, alongside 191 frontend tests,
  inside the Docker test image. Backend line coverage 97% overall, with every file clearing
  the project's 90% per-file gate. The skips are the real-engine tests, which need a live
  service and a GPU; all 177 of them ran on hardware against this tree.
- **Hardware matrix: 23 of 23 rows passed** across four machines -- every engine, vocal
  isolation on and off, and every accelerator the fleet can reach.
- **Device attribution was then re-established separately**, because those 23 rows did not
  actually prove it. The runner recorded the startup banner, which names the device that was
  *requested*; only `/status` names the device an inference touched, and the two disagree
  precisely when something has silently fallen back. Fifteen further rows re-ran every
  preprocessing claim with the measured figure captured, and their logs are committed under
  `docs/validation/v1.3.0/`. Where a row's accelerator shows `measured: false`, or shows
  `true` on an architecture the image ships no kernels for, it is called out rather than
  counted -- see Known Limitations.
- **Cold-build check**: all nine targets build with `--no-cache`, re-verified on the final
  tree -- 9 of 9, after the last Dockerfile change rather than before it. A separate claim
  from the suite, and it needs to be: the build cache hides exactly the class of failure it
  catches, which is how v1.3.0 came to be unbuildable in the first place.
  The sweep also found a real one. `amd-rocm-torch`, the heaviest target, failed five
  consecutive cold builds with `ReadTimeoutError` -- a different package every time and never
  a resolution error -- while the same `deps-cpu` stage built alone passed every time. The
  cause is concurrency inside the build: BuildKit runs `ort-builder`'s four ONNX Runtime
  wheels, the apt fetches and the multi-gigabyte torch resolve at once, and on that target it
  exhausts the connection. Poetry's installer now uses two workers rather than four, which is
  the part of that contention this repository controls, and the target has built cleanly
  twice since.
- **Intel NUC** (Core Ultra, Arc iGPU + AI Boost NPU): **8/8 rows**, covering INTEL-WHISPER
  with vocal isolation on the iGPU and on the NPU, FASTER-WHISPER keeping the Intel unit in
  the pool while ASR falls to the CPU, an explicit `ASR_DEVICE=NPU` request being refused by
  the executability probe, OPENAI-WHISPER on the XPU image, and a CPU baseline. UVR reports
  `[ONNX provider: OpenVINOExecutionProvider]` on `Intel(R) AI Boost` -- a provider name, not
  a transcript.
- **RTX 5090 via Windows 11 / WSL2**: **5/5 rows** -- all four engines on CUDA, vocal
  isolation on and off, and the 20-minute long-form clip. Evidence for the CUDA claim is
  `Context: NVIDIA CUDA`, `[ONNX provider: CUDAExecutionProvider]`, isolation at 2.18x,
  `/status` reporting both stages `measured` rather than predicted, and `nvidia-smi`
  compute-apps sampled while a transcription was in flight.
- **RTX 3080 + Intel UHD laptop** (`nvidia-intel`): both scheduler slots filled, and the
  dashboard reporting `Inference: CUDA (measured)` and `Vocal Isolation: CUDA (measured)`
  for the NVIDIA unit with isolation at 2.66x -- the hybrid arrangement this release fixes.
- **RTX 5090 on Linux** (NVIDIA + integrated Radeon): **6/6 rows** -- the complete
  156-language matrix (158 passed), long-form stress, WHISPERX, OPENAI-WHISPER, vocal
  isolation off, and the `full` image. `full` is the only row no other machine can run: its
  override passes `/dev/kfd`, and Compose refuses to start when a listed device is absent, so
  it needs a host that genuinely has an AMD GPU.
- **Windows 11 / WSL2** on the same host: the remote path exercised end to end, including
  Windows profile resolution read from the host rather than assumed.
- A passing suite proves decoding worked, not that the accelerator was used. Accelerator
  claims in this release are backed by device-side evidence — provider names, `nvidia-smi`
  compute apps, `intel_gpu_top`, or the worker's own reported provider.
