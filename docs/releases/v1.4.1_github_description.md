# Release v1.4.1 - Static Analysis in the Pipeline, and a Dependency Sweep

A maintenance release, and a larger one than that usually implies: alongside the
dependency sweep and the static-analysis wiring, `scripts/` is now measured by coverage
for the first time. Nothing in the engine, the decoding path or the language handling
changes, and the API contract is unchanged. Transcripts were not diffed against v1.4.0
request-for-request, so that is the claim being made rather than bit-identical output:
the upload path and several dependencies did move, and both sit upstream of a decode.

Two things moved. Every dependency without a hardware-backed reason to stay put was
brought to its current release, and SonarQube Cloud now analyses the tree on every push
and pull request -- and, for the first time, gets told where the coverage reports are.

---

## Highlights

### SonarQube Cloud Analysis

The `sonarqube` job runs after the two coverage-producing stages, uploads the Python
`coverage.xml` and the JavaScript `lcov.info` alongside the source, and enforces the
quality gate. Both publish jobs now depend on it, so a failed gate stops a release rather
than being noticed afterwards.

Wiring it up surfaced that `js-unit-tests` had been generating an lcov report inside the
container and discarding it when the container exited -- the JS coverage number existed
for the duration of the stage and was then thrown away. It is now exported and uploaded,
which is what lets the analysis report JavaScript coverage at all.

The same configuration drives a local run, deliberately: `sonar-project.properties` holds
the sources, exclusions and report paths, and `scripts/sonar_scan_local.sh` supplies only
the host, the token and the branch. A developer scanning before pushing applies the same
rules to the same files as CI, rather than discovering the difference in a failed gate.

Analysis runs with a full clone (`fetch-depth: 0`). A shallow one leaves SonarQube unable
to assign blame, which is what new-code detection and the pull-request gate are computed
from.

### scripts/ Is Now Measured By Coverage

`.coveragerc` omitted `scripts/*`, so the fixture generator, the audio catalog, the model
preloader and the audio-matrix toolchain were unmeasured -- 1,532 statements at 37%, with
17 of 18 files below the threshold every other file in the project is held to. The omit is
gone and each of those files now passes the same per-file 90% gate as `modules/`.

That took roughly 350 new tests. They are weighted towards the failures these modules'
own comments already record, because in almost every case the comment was the only thing
enforcing the behaviour:

- the audio-matrix cache treats a truncated stamp as stale rather than aborting a whole
  generation over one sidecar
- `-t` is an output-side cap, because a duration attached to the wrong filter element
  silently produces an unbounded render from a generator that never ends
- the concat listing is removed even when ffmpeg fails, because a stray `.concat.txt`
  makes a regeneration report a dirty tree that has nothing to do with the audio
- the long-form builder registers each part before rendering it, because the numbered
  files it writes are the exact names the next attempt writes
- `.partial` goes before the extension, because ffmpeg picks its muxer from it
- the stress profile takes one clip per language, because it cycles its source list to
  alternate -- three per language once took that fixture from 118 utterances switching at
  every boundary to 117 switching at 78 of 116, changing the artifact every recorded
  `windows` measurement is stated against

The three security fixes above are among the code this now covers: the path-traversal
guard, the division-by-zero guard and the private temporary directory all landed in
`scripts/`, and all three were untested when they were written.

`sonar-project.properties` carries no coverage exclusion for `scripts/` either, so the
quality gate measures it too.

### What Was Deliberately Not Updated

**torch stays at 2.13.0 and torchvision at 0.28.0.** 2.14.0 and 0.29.0 are available and
were skipped on purpose. torch 2.14 resolves the CUDA 13 wheel set, while
`scripts/docker/install_cuda.sh` pins `libcublas-12-9` because libctranslate2 dlopens
`libcublas.so.12` by name. That mismatch is invisible to the test suite -- every test mocks
the engine, so the suite stays green and the image still builds, and then every
torch-engine request returns HTTP 500. The existing pin comment records the measurement
this is based on; nothing in this release changes it.

librosa/audio-separator and numpy were already at their current releases and did not move.

### Validated on Real Hardware

Every accelerator the bumps could touch was driven with real speech over HTTP, and the claim
is the per-request device line rather than the startup banner:

| | evidence | suite |
| --- | --- | --- |
| Intel **NPU** (UVR) | `Intel(R) AI Boost [ONNX: OpenVINOExecutionProvider]` @ 3.97x | 28 passed, 2 failed |
| Intel **GPU** (UVR) | `Intel(R) Graphics [0x7d51] (iGPU) [OpenVINOExecutionProvider]` @ 0.72x | 28 passed, 2 failed |
| **CUDA** (RTX 5090) | `CUDA (float16)` on `cuda:0`, UVR on `CUDAExecutionProvider` @ 13.1x | 30 passed, 0 skipped |

The two Intel failures (`mix_en_fr`) and a native crash seen on an older TigerLake iGPU were
each re-run against pristine v1.4.0 in the same configuration and reproduce there exactly, so
both predate this release. They are open defects, documented with their evidence in
`docs/validation/v1.4.1/`, not regressions from the sweep.

`mix_en_fr` passes on CUDA, so the failure is specific to the INTEL-WHISPER engine rather
than to the clip, the harness or Intel device routing.

Not proven: CUDA on the local RTX 3080 (that host's driver returns `CUDA_ERROR_NO_DEVICE` to
containers) and AMD (no hardware).
